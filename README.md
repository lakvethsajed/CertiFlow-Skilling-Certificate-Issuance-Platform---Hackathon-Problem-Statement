# CertiFlow

CertiFlow manages Training Centre submissions, District Officer approvals, and Quality Team reviews. The frontend uses React, Vite, and custom CSS. The API uses FastAPI, Pydantic, SQLAlchemy 2, Alembic, and PostgreSQL.

## Run locally

Use Python 3.11 or later, Node.js 20.19 or later for Vite, and a PostgreSQL database owned by your development user.

```sh
cd backend
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
```

The virtual environment isolates Python dependencies to this workspace. For a fresh setup, copy `.env.example` to `.env`, set `DATABASE_URL`, and set `JWT_SECRET` to a value generated by `openssl rand -hex 32`. Preserve an existing secret across a cutover if you want existing sessions to remain valid.

On an **empty PostgreSQL database**, apply the migrations and start the API:

```sh
.venv/bin/python -m alembic upgrade head
.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 3001
```

Alembic creates or upgrades the schema. Uvicorn serves the FastAPI application. For an existing Phase 2 database, follow the migration procedure below before starting the API.

In a second terminal:

```sh
cd frontend
npm ci
npm run dev
```

Open [CertiFlow](http://127.0.0.1:5173/). Vite forwards `/api` to port 3001. If the workspace's local PostgreSQL cluster is stopped, restart it from the repository root on this Mac:

```sh
'/Library/PostgreSQL/18/bin/pg_ctl' -D "$PWD/.certiflow-local/postgres" -l "$PWD/.certiflow-local/postgres.log" -o "-h 127.0.0.1 -p 55433 -k ''" start
```

For deployment, serve the built frontend with an SPA fallback and reverse-proxy `/api` under the same HTTPS origin. Set `APP_ORIGIN` and `NODE_ENV=production`. Enforce an IP-based login limit at the production reverse proxy when running multiple workers.

## Workflow and code walkthrough

- `Workspace` in `frontend/src/main.jsx` uses the authenticated role to render workspace routes inside `Layout`. Routes for Quality Team appear after signing in as Neha.
- `QualityDashboard` reads `qualityApi.dashboard` and renders linked counts and recent activity. `QualityQueue` keeps search, filters, sorting, and pagination in the URL. It loads matching revisions through `qualityApi.list` and passes the result to `QualityQueueTable`.
- `QualityDetails` passes the selected batch ID and revision to `QualityRevision`. That component fetches details, tracks the selected action, and renders `StudentPreview`, `DistrictValidation`, `ApprovalProgress`, and `ApprovalHistory`. The candidate table manages its own search, validation filter, sort order, and page. The shared `DecisionDialog` validates the comment and calls `qualityApi.decide`. Success updates the displayed revision; errors remain visible in the dialog. The pages use the existing styles in `frontend/src/styles/global.css`.
- The FastAPI router in `backend/app/routers/workflow.py` validates inputs and selects a service. Dependencies in `backend/app/dependencies.py` verify the JWT, look up the stored session and role, and provide a SQLAlchemy session. The Training Centre and District Officer queries apply organisation scope before returning data.
- On the second distinct district approval, `services/district.py` counts persisted candidates on that revision. With the default `QUALITY_THRESHOLD=50`, exactly 50 candidates go directly to State Office and exactly 51 go to Quality Team. Queue and eligibility checks run on the server.
- `services/quality.py` locks the batch row, rechecks eligibility, and saves the decision, new status, and audit event in one transaction. A database primary key on the reviewed revision prevents a second final quality decision. A return creates no new revision until the centre resubmits. The new revision requires fresh district and, when eligible, quality approval. No background worker is required.

## Migrate an existing Phase 2 database

1. Back up PostgreSQL and restore it into a disposable database. Compare that schema to a fresh test database migrated to `0001_phase2`, excluding the two migration-history tables.
2. On the verified copy, run `python -m alembic stamp 0001_phase2` to record the schema already present. Run `python -m alembic upgrade head` to add the quality review tables and audit rules. Run `python -m alembic check` to detect schema differences. Each command should be run with `DATABASE_URL` explicitly pointing to the copy.
3. Run `python -m app.reconcile_quality` for a dry run. This checks legacy quality queues using actual candidate counts and district approvals. `--apply` writes reconciled routing and a system audit event. Any inconsistent batch blocks the apply operation for manual review.
4. After copying, testing, and backing up the real database, stop the prior API. Run the same stamp, upgrade, and reconcile steps against the real database, then start FastAPI on port 3001. The migrations preserve Phase 2 rows and Prisma's original migration history.

## Verification

Set `TEST_DATABASE_URL` to an isolated PostgreSQL database. The integration suite creates records there and leaves them for inspection.

```sh
cd backend
DATABASE_URL="$TEST_DATABASE_URL" .venv/bin/python -m alembic upgrade head
DATABASE_URL="$TEST_DATABASE_URL" .venv/bin/python -m alembic check
TEST_DATABASE_URL="$TEST_DATABASE_URL" .venv/bin/python -m pytest -q
```

The tests cover threshold boundaries, role and district access, upload validation, returns and fresh approvals, rejection, audit history, and concurrent quality decisions. In `frontend/`, run `npm test`, `npm run lint`, `npm run format:check`, and `npm run build`.

## Student activation (Phase 6)

Apply migration `0008_student_secret_codes` before using the new flow.
Candidate upload still accepts the existing CSV columns and creates no login
accounts. After submitting the batch, the owning Training Centre opens
**My Batches → Batch Details → Download Activation Codes**. That action issues
the codes and returns them once in a private CSV containing `student_id`,
`student_name`, `course_name`, and `activation_code`. Previously submitted batches use the
same action to issue their first codes. There is no email delivery step.

Give each student only their own code through a private channel. The app
stores a keyed hash, so a second export cannot retrieve the original codes.
To replace a lost or expired code, enter the Student ID in the same batch
details panel and click **Regenerate and Download**. The old code and any
password setup grant for it become invalid. Issuance and regeneration are
audited. Students who already have accounts are skipped.

Codes expire after 30 days by default. Set `STUDENT_ACTIVATION_DAYS` to change
the lifetime for new codes. Only current finally approved candidate revisions
can activate. Conflicting approved emails for one Student ID require staff
resolution. Successful verification returns a five-minute password setup
grant. Account creation and consumption of the code commit together.

| Endpoint | Input |
| --- | --- |
| `POST /api/centre/batches/{batch_id}/activation-codes/export` | Owning Training Centre session |
| `POST /api/centre/batches/{batch_id}/activation-slips` | Owning Training Centre session; one-time printable PDF for unexported rows |
| `POST /api/centre/batches/{batch_id}/candidates/{candidate_id}/activation-slip` | Owning Training Centre session; one-time PDF for a candidate in the current revision |
| `POST /api/centre/batches/{batch_id}/activation-codes/regenerate` | Owning Training Centre session and `student_id` |
| `POST /api/student/activation/verify` | `student_id`, `activation_code` |
| `POST /api/student/activation/complete` | `grant`, `password`, `confirm_password` |

CSV and PDF downloads share the same one-time export. If a student's code
was already downloaded in either format, the other format cannot recover it.
The PDF uses three slips per A4 page and links to the activation page at
`APP_ORIGIN`. Use a student-accessible HTTPS origin for remote distribution.
A generated PDF or CSV contains credentials and must be shared privately.

Existing accounts retain their registered email and password. Legacy OTPs
and OTP-based password setup grants can no longer activate accounts.

From `backend/`, use a disposable PostgreSQL database for tests:

```sh
DATABASE_URL="${TEST_DATABASE_URL:?Set the disposable test database URL}" .venv/bin/python -m alembic upgrade head
TEST_DATABASE_URL="$TEST_DATABASE_URL" .venv/bin/python -m pytest -q tests/test_student_activation.py
```

### Student sign-in and password management

| Endpoint | Input |
| --- | --- |
| `POST /api/student/auth/login` | Registered `email` and `password` |
| `POST /api/student/auth/change-password` | `current_password`, `password`, `confirm_password` |
| `POST /api/student/auth/logout` | Student session cookie |

Student and staff sign-in use the same JWT cookie and PostgreSQL session
table. Student sign-in requires an active Candidate-linked account.
Password changes require the current password and revoke all sessions for
that student. Sign in again with the new password. Logout revokes the
current session. The existing `GET /api/auth/session` endpoint can restore
a student session in the frontend.

To test activation and sign-in together, run
`TEST_DATABASE_URL="${TEST_DATABASE_URL:?Set the disposable test database URL}" .venv/bin/python -m pytest -q tests/test_student_activation.py`
from `backend/`.

### Student profile and private certificates

These read-only endpoints require an activated student session.

| Endpoint | Result |
| --- | --- |
| `GET /api/student/profile` | The signed-in student's profile and certificate count |
| `GET /api/student/certificates?page=1&page_size=20` | A page of the student's certificates |
| `GET /api/student/certificates/{id}` | Details and status for an owned certificate |
| `GET /api/student/certificates/{id}/download` | An attachment for an owned, active PDF |

The API derives ownership from the authenticated account's approved Candidate
anchor and its normalized Student ID and registered email. Certificate
queries compare both values against the persisted Candidate snapshot.
Unrelated IDs return 404. Cancelled certificates can still appear in the
student's list, but their PDFs are unavailable. The legacy public
verification endpoint keeps its existing behavior.

After migration `0007_candidate_certificate`, an operator can process an
already-approved batch from `backend/`:

```sh
.venv/bin/python -m app.issue_candidate_certificates <batch-uuid>
```

This local command requires the stored State Office approval and issuance
request. It locks the batch while writing one certificate per candidate,
and can be rerun without adding duplicate records. Set `CERTIFICATE_STORAGE`
to a private absolute directory to override the workspace default
`.certiflow-local/certificates`. Keep this directory outside static web
roots. Portal requests only read issued records and PDFs. This step does
not add an automatic issuance worker or public verification of candidate PDFs.

### Student Portal walkthrough

Open [Student Portal](http://127.0.0.1:5173/student/login) or use **Student
Portal** on the staff sign-in screen. Select **Activate account**, enter the
Student ID and private activation code from your Training Centre, then set a
password. Sign in with your registered email and password.
The certificate dashboard shows a real empty state until an operator issues
certificates for the approved batch. Once issued, select **View Certificate**
or **Download PDF**. **Profile** shows registration details and lets the
student change their password.

- `App` restores the existing session and renders student routes only for an
  authenticated Candidate. The shared `Login` form uses its `student` prop to
  choose the correct sign-in API. Staff sessions must sign out to switch.
- `StudentActivation` renders the Student ID and secret code fields, then the
  password form. React keeps the short-lived grant in component memory and
  submits it through `studentApi`.
- `StudentWorkspace` renders `StudentLayout` and its dashboard, details, and
  profile routes. The dashboard loads the profile and passes it to
  `ProfileCard`. `CertificateList` keeps the page in the URL and passes each
  returned certificate to `CertificateRecord`. Its download button requests a
  PDF through the same browser session. The profile form reuses the activation
  password fields and returns the student to sign-in after a password change.
- FastAPI validates request bodies. SQLAlchemy joins certificate records to
  the Candidate snapshots that match the signed-in student's approved
  identity. The download route checks ownership and status again before
  sending the file. The portal uses the shared CertiFlow styles and
  `frontend/src/styles/student.css` for its layout.

The full backend suite covers activation, student sign-in, password changes,
PDF access, cross-student authorization, and the existing staff workflows.
Use a fresh disposable PostgreSQL database, apply Alembic with its URL, and
run the existing `pytest` command from `backend/`. From `frontend/`, run
`npm run lint`, `npm run format:check`, `npm test`, and `npm run build`.
